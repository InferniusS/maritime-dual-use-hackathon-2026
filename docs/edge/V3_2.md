## Persistent data upgrade

On first opening a pre-3.2 session database, the store preserves its exact previous session JSON in `engineering_migrations.source_snapshot`. It keeps all original pipe coordinates, dimensions, proposal history and audit history. Old cached analysis is invalidated, pending/approved proposals become stale, and the session revision advances once with an `engineering_assurance_upgraded` audit event.

Old numeric dumps cannot reveal which dimensions or coefficients originally came from defaults. Missing provenance is therefore qualified conservatively, rather than promoting old cached PASS results. Re-establish authoritative metadata and reconnect existing native sessions with `PFCONNECT`. The original DWG is never rewritten by this migration. Reopening the database again does not repeat the migration.

New JSON models retain `metadata_missing` through serialization. Replacing an assumption requires supplying its actual value and deliberately removing that field from the missing list in the newly validated input. For example, a supplied outside diameter does not automatically establish a missing bore or fitting coefficient. Procedural fixtures now explicitly declare their illustrative physical/catalog values; their existing routing and hydraulic checks remain reproducible.

## Review, export and companion

The companion displays extraction scope and unresolved objects, four-state candidate validation, measured/required values, clearance evidence and failed-search reasons even when no proposal exists. Endpoint tolerances retain scientific-scale precision. Known incomplete CAD scope disables approval/export while diagnostic preview and rejection remain available; unverified explicit-model calculations remain visibly qualified.

Coverage includes a monotonic `source_generation`, so an unknown geometry edit invalidates an old approval even when entity counts and modeled coordinates have not changed. Approved exports recheck the current source after generation. The session-only apply endpoint refuses native-owned sources; CAD edits must be confirmed by the connector's source revision.

The native adapter preserves transient diagnostic preview, unit conversion, the shared-session browser bridge and read-only source access. Native approval/export requires complete declared extraction scope. Live block/xref and nested-entity bindings are rejected until their dependency semantics are supported. A maximum 10,000 scoped CAD entities prevents an unbounded UI-thread coverage scan. Unbound annotations remain explicitly unresolved too; there is no implicit-ignore policy or ignore editor yet, so native approval currently requires a fully mapped, explicitly scoped modelspace. See [AUTOCAD.md](AUTOCAD.md).

## Processing and access

Start the main application as before with `./scripts/start.sh`, or the existing PowerShell scripts on Windows. Start the optional local CPU worker with `PIPEFORGE_PYTHON=/workspace/pipeforge-venv/bin/python ./scripts/start-edge.sh` in the prepared cloud workspace. It now binds loopback by default. For a shared LAN worker, configure an explicit listening address plus `PIPEFORGE_EDGE_TOKEN` or `PIPEFORGE_EDGE_ALLOWLIST`; see [REMOTE.md](REMOTE.md) for complete commands and limits. Enter the matching token in the companion's memory-only password field, or supply `PIPEFORGE_REMOTE_TOKEN` to the processing client environment. Never put credentials in URLs or model JSON.

Work limits cover local analysis/search, remote requests, independent verification, fallback and publication. Exceeding a limit returns an explicit failure/unresolved condition; no passing result is created by truncation. Defaults and hard bounds are documented in REMOTE.md. CPU deadlines and cancellation are cooperative, not operating-system process termination. Already dispatched remote work has no cancellation endpoint; its own limits remain enforced.
